# Checking TROs via GitHub Actions

tro-checks provides five GitHub Actions workflows which can be installed into consuming repos via `make install-tro-checks-gha`. These workflows enable checks of TRO declarations without installing any software. They also automate some tasks that `make` in a clone does not, such as making the reports again whenever the candidates change. 

## The workflows

To start a workflow by hand, open the repository's Actions tab on GitHub, select the workflow, and click *Run workflow*. GitHub then shows a form with the workflow's text boxes, drop-downs and checkboxes; the run starts when the form is submitted.

**Preview pasted declaration.** Runs tro-checks against a TRO declaration pasted into a text box, for the TRACE version and tier given on the form. The resulting report appears only on the run's page, nothing is committed, and the run can be deleted afterwards. **Automatic triggering:** None.

**Preview one candidate.** Runs tro-checks against one candidate declared in the repository. The name of the candidate file, the TRACE version and the tier are entered in the workflow's form; the version and tier may differ from those in the entry for the candidate in the manifest. The resulting report appears only on the run's page, and nothing is committed. **Automatic triggering:** None.

**Regenerate reports.** Runs tro-checks against every candidate declared in the repository, for each target named in the entry for the candidate in the manifest, using the repository's own image, and shows the combined report on the run's page. A checkbox, ticked by default, controls whether the new reports should be committed to the repository on GitHub. Each run that reports on the candidates builds the repository's image afresh so that the reports show how candidates fare against the latest version of tro-checks. **Automatic triggering:** In addition to supporting manual runs with options set on its form, this workflow starts automatically whenever commits are pushed to GitHub (including edits made on github.com and merged pull requests). When started automatically, it first determines whether the reports are already up to date with the candidates and manifest, and stops if they are. It also stops if *Regenerate candidates* is installed and will regenerate the candidates, and with them the reports. Otherwise, it brings the reports up to date and commits them to the repository on GitHub.

**Regenerate candidates.** Generates the candidates again with the repository's `generate-candidates.sh`, then runs tro-checks against them as *Regenerate reports* does. A checkbox, unticked by default, controls whether the new candidates and reports should be committed to the repository on GitHub. The workflow is installed only in repositories that generate their own candidates. **Automatic triggering:** This workflow also starts automatically whenever commits are pushed to GitHub. When started automatically, it first determines whether the candidates' dependencies have changed since the candidates were last generated, and stops if they haven't. Otherwise, it regenerates the candidates and reports and commits them to the repository on GitHub. The dependencies are the `Dockerfile`, `generate-candidates.sh`, and the files in `resources/` other than READMEs, so a push that changes the version of the tool that generates the candidates, for example, regenerates them. Candidates generated with `make generate-candidates` in a clone and then pushed count as up to date.

**Pull candidates.** Copies candidates from other repositories that use tro-checks, as listed in the repository's `pull-list.json`, then runs tro-checks against them as *Regenerate reports* does. Each line of the pull list names a source repository and one of its candidates, and optionally applies settings renaming or retargeting each pulled candidate. A checkbox controls whether the copied candidates and new reports should be committed to the repository on GitHub. This workflow is installed only in repositories that collect candidates from others, such as a showcase of TROs from different organizations and tools. **Automatic triggering:** None.
