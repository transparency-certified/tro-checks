# Reporting on TROs with GitHub Actions

tro-checks provides five GitHub Actions workflows which can be installed into consuming repos via `make install-tro-checks-gha`. These workflows enable checks of TRO declarations without installing any software. They also automate some tasks that `make` in a clone does not, such as making the reports again whenever the candidates change.

[`spec-tro-checks`](https://github.com/transparency-certified/spec-tro-checks) is an example of a repository using *Regenerate reports*, *Preview one candidate* and *Preview pasted declaration*.

## The workflows

| Workflow | What it's for |
|---|---|
| [Preview pasted declaration](#preview-pasted-declaration) | Quickly see how any TRO declaration fares against the TRACE Specification |
| [Preview one candidate](#preview-one-candidate) | See how a candidate would fare against a TRACE version or tier different from the ones it currently targets |
| [Regenerate reports](#regenerate-reports) | Update reports for all candidates |
| [Regenerate candidates](#regenerate-candidates) | Regenerate any automatically created candidates and update their reports |
| [Pull candidates](#pull-candidates) | Recopy any candidates pulled from other repositories and update their reports |

### Preview pasted declaration

One often wants quick feedback on whether a TRO declaration meets the expectations of the TRACE Specification. This workflow runs tro-checks against a TRO declaration pasted into a text box, for the TRACE version and tier given on the form. The resulting report appears only on the run's page, nothing is committed, and the run can be deleted afterwards. **Automatic triggering:** None.

| | |
|---|---|
| Starts | By hand |
| Reads | The pasted declaration |
| Commits | Nothing |
| Installed with | `make install-tro-checks-gha -- preview-pasted-declaration` |

---

### Preview one candidate

It can be useful to see how a candidate would fare against a TRACE version or tier it doesn't currently target. This workflow runs tro-checks against one candidate declared in the repository. The name of the candidate file, the TRACE version and the tier are entered in the workflow's form; the version and tier may differ from those in the entry for the candidate in the manifest. The resulting report appears only on the run's page, and nothing is committed. **Automatic triggering:** None.

| | |
|---|---|
| Starts | By hand |
| Reads | The candidate file; `candidates/manifest.json` |
| Commits | Nothing |
| Installed with | `make install-tro-checks-gha -- preview-one-candidate` |

---

### Regenerate reports

Reports go out of date whenever the candidates change or tro-checks does. This workflow runs tro-checks against every candidate declared in the repository, for each target named in the entry for the candidate in the manifest, using the repository's own image, and shows the combined report on the run's page. A checkbox, ticked by default, controls whether the new reports should be committed to the repository on GitHub. Each run that reports on the candidates builds the repository's image afresh so that the reports show how candidates fare against the latest version of tro-checks. **Automatic triggering:** In addition to supporting manual runs with options set on its form, this workflow starts automatically whenever commits are pushed to GitHub (including edits made on github.com and merged pull requests). When started automatically, it first determines whether the reports are already up to date with the candidates and manifest, and stops if they are. It also stops if *Regenerate candidates* is installed and will regenerate the candidates, and with them the reports. Otherwise, it brings the reports up to date and commits them to the repository on GitHub.

| | |
|---|---|
| Starts | On a push to any branch; by hand |
| Reads | `candidates/`; `reports/last-generated.json`; when *Regenerate candidates* is installed, what it reads too |
| Commits | `reports/`, to the pushed branch, after a push or when *Commit* is ticked |
| Installed with | `make install-tro-checks-gha -- regenerate-reports` |

---

### Regenerate candidates

Candidates generated by a tool go out of date whenever the tool, or what it generates them from, changes. This workflow generates the candidates again with the repository's `generate-candidates.sh`, then runs tro-checks against them as *Regenerate reports* does. A checkbox, unticked by default, controls whether the new candidates and reports should be committed to the repository on GitHub. The workflow is for repositories that generate their own candidates. **Automatic triggering:** This workflow also starts automatically whenever commits are pushed to GitHub. When started automatically, it first determines whether the candidates' dependencies have changed since the candidates were last generated, and stops if they haven't. Otherwise, it regenerates the candidates and reports and commits them to the repository on GitHub. The dependencies are the `Dockerfile`, `generate-candidates.sh`, and the files in `resources/` other than READMEs, so a push that changes the version of the tool that generates the candidates, for example, regenerates them. Candidates generated with `make generate-candidates` in a clone and then pushed count as up to date.

| | |
|---|---|
| Starts | On a push to any branch; by hand |
| Reads | `Dockerfile`, `generate-candidates.sh`, `resources/`; `candidates/last-generated.json` |
| Commits | `candidates/` and `reports/`, to the pushed branch, after a push or when *Commit* is ticked |
| Installed with | `make install-tro-checks-gha -- regenerate-candidates` |

---

### Pull candidates

Reports for candidates copied from other repositories go out of date whenever their sources change. This workflow copies candidates from other repositories that use tro-checks, as listed in the repository's `pull-list.json`, then runs tro-checks against them as *Regenerate reports* does. Each line of the pull list names a source repository and one of its candidates, and optionally applies settings renaming or retargeting each pulled candidate. A checkbox controls whether the copied candidates and new reports should be committed to the repository on GitHub. This workflow is for repositories that collect candidates from others, such as a showcase of TROs from different organizations and tools. **Automatic triggering:** None.

| | |
|---|---|
| Starts | By hand |
| Reads | `pull-list.json`; `candidates/manifest.json`; each source's `candidates/` |
| Commits | `candidates/` and `reports/`, to the branch it ran on, when *Commit* is ticked |
| Installed with | `make install-tro-checks-gha -- pull-candidates` |

## What a repository needs

The workflows run in a REPRO: a repository with the repros `Makefile` and a `repro-config`, whose `Dockerfile` requires tro-checks.

**The `Dockerfile`** requires the tro-checks module:

```
ENV TRACE='https://raw.githubusercontent.com/transparency-certified/${1}/${2}/exports'
RUN repro.require tro-checks main ${TRACE} --report
```

**`repro-config`** includes tro-checks' make targets, and, for now, a rule that sets the module's files up the first time one of its targets is needed in a fresh clone:

```make
# Add tro-checks' make targets if the tro-checks module has been initialized.
-include .tro-checks/host-makefile

# Temporary, until repros sets up a module's files the first time one of its targets is needed.
# The make it runs sets SETTING_UP_MODULES, so it doesn't try again itself.
ifndef SETTING_UP_MODULES
.%/host-makefile:
	$(if $(REPRO_IMAGE_ID),$(MAKE) init-repro SETTING_UP_MODULES=true)
endif
```

**`.gitignore`** must not ignore `.github/`. A `.gitignore` that ignores dot files with `.*` needs `!.github/` after it.

**`candidates/manifest.json`** declares the candidates, as described in the [README](../README.md#usage).

**For *Regenerate candidates*:** a `generate-candidates.sh` at the top of the repository, run in the image from the top directory, which writes the candidates' files in `candidates/` and deletes any it no longer generates; `candidates/manifest.json` declares them as for any other candidates. And a `resources/` directory holding what it reads, such as the generating tool's pinned version and the inputs to each candidate. These, with the `Dockerfile`, are the candidates' dependencies.

**For *Pull candidates*:** a `pull-list.json` at the top of the repository, a JSON array with one object for each candidate to pull:

```json
[
    {
        "source": "transparency-certified/spec-tro-checks",
        "candidate": "03-spec-example-2026-04-08-with-node-ids",
        "name": "spec-03",
        "target": [{ "tier": "LINKABLE-TRO", "version": "trace-main" }]
    }
]
```

| Field | |
|---|---|
| `source` | The source repository, as `owner/name`. Required. |
| `candidate` | The candidate's name in the source's manifest. Required. |
| `ref` | The branch or tag to pull from. Default: the source's default branch. |
| `name` | The candidate's name here. Default: its name in the source. |
| `target` | Its target or targets here, in the manifest's form. Default: its targets in the source. |

## What the workflows assume

- The workflows that write own `candidates/` and `reports/`: they replace what they generate, and commit any change to the branch they ran on.
- Their commits are made by `github-actions[bot]` with the run's `GITHUB_TOKEN`. GitHub starts no workflow for a push made that way, so a commit of new reports does not start *Regenerate reports* again.
- Each job that needs the image builds it on the runner with `make build-image`, except *Regenerate candidates*' `generate-reports`, which loads the image `generate-candidates` built. No layer cache is kept between runs, so every build fetches tro-checks again.
- *Regenerate reports* and *Regenerate candidates* coordinate by file name: on a push, *Regenerate reports* stands down when `.github/workflows/regenerate-candidates.yml` exists and the candidates' dependencies have changed.
- The runner is `ubuntu-latest`, which provides `jq` and `git`, used by the scripts.
- The two *Preview* workflows offer the TRACE versions and tiers tro-checks had when they were installed.

## Installing and updating

In a clone of the repository, with the image built, each workflow is installed by naming it:

```
make install-tro-checks-gha -- regenerate-reports preview-one-candidate
```

installs those two workflows, with the actions, scripts and data they use, and nothing else. `make list-tro-checks-gha` lists the workflows and says which are installed. What each workflow consists of is described in the workflow catalog, [`exports/workflow-catalog.json`](../exports/workflow-catalog.json).

The workflows are copied from the tro-checks module in the image, so updating them means rebuilding the image, so that it fetches tro-checks again, then updating the workflows installed:

```
make build-image
make update-tro-checks-gha
```

An install or update overwrites the files it writes, including any edits made to them. It removes nothing: a workflow is removed by deleting its file, and a file no installed workflow uses any more stays until deleted.

## Installed files

| File | What it is |
|---|---|
| `.github/workflows/<workflow>.yml` | The workflows |
| `.github/tro-checks-version` | The branch or tag of tro-checks the image required when the workflows were installed or updated |
| `.github/actions/show-run-record/action.yml` | Writes the run record at the top of the run's page |
| `.github/actions/check-tro-declaration/action.yml` | Builds the image and reports on one declaration against a version and tier |
| `.github/scripts/describe-tro-checks` | Names the tro-checks commit the image will be built with, for the run record |
| `.github/scripts/tier-title` | Gives a tier's title, e.g. `Tier 6 - STANDALONE-TRO` |
| `.github/scripts/version-tiers` | Lists a TRACE version's tiers |
| `.github/scripts/candidate-file` | Finds a candidate's file from its name |
| `.github/scripts/hash-candidates` | Hashes every file in `candidates/` |
| `.github/scripts/candidates-changed` | Says whether the candidates changed since the reports were last generated |
| `.github/scripts/hash-candidate-dependencies` | Hashes the candidates' dependencies |
| `.github/scripts/candidate-dependencies-changed` | Says whether the candidates' dependencies changed since the candidates were last generated |
| `.github/scripts/resolve-pull-list` | Finds the commit and manifest entry of each candidate in `pull-list.json` |
| `.github/scripts/copy-pulled-candidates` | Copies the pulled candidates into `candidates/` |
| `.github/versions/<version>/tiers.json` | The tiers of each TRACE version tro-checks has |

Which workflows use which of these is described in the workflow catalog, [`exports/workflow-catalog.json`](../exports/workflow-catalog.json).

## Make targets

`repro-config`'s include adds these targets, each run in the image:

| Target | What it does |
|---|---|
| `make generate-candidates` | Runs `generate-candidates.sh`, then writes `candidates/last-generated.json` |
| `make generate-tro-reports` | Deletes the reports on single TRO declarations (`reports/*__to__*.md`), then writes one report per target of each candidate, `reports/README.md`, `reports/integrated-report.md` and `reports/last-generated.json` |
| `make clean-tro-reports` | Deletes the reports on single TRO declarations |
| `make list-tro-checks-gha` | Lists the workflows tro-checks provides, and which are installed |
| `make install-tro-checks-gha -- <workflow>...` | Installs the workflows named, as above |
| `make update-tro-checks-gha` | Updates the installed workflows, as above |

The repros target `make build-reports` runs every module's report step, tro-checks' among them. For tro-checks it writes the same files as `make generate-tro-reports`, `reports/last-generated.json` included, without first deleting the old reports.

## The records

Two files record what the candidates and the reports were last generated from. Both are JSON objects with two members: `tro-checks`, the branch or tag of tro-checks the image required, and `hash`, a SHA-256 hash.

| File | Its `hash` is of | Written by | Read by |
|---|---|---|---|
| `reports/last-generated.json` | Every file in `candidates/`, the manifest and `candidates/last-generated.json` included | `make generate-tro-reports`, `make build-reports` | `candidates-changed`, so *Regenerate reports* |
| `candidates/last-generated.json` | The `Dockerfile`, `generate-candidates.sh` and the files in `resources/`, READMEs left out | `make generate-candidates` | `candidate-dependencies-changed`, so *Regenerate reports* and *Regenerate candidates* |

The hashes are made by the scripts the workflows run to decide whether the reports or the candidates are up to date, so reports or candidates generated in a clone and pushed count as up to date.
